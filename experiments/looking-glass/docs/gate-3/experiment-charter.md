# Gate 3 pre-browser experiment charter

Version `gate-3-charter-v1`. Root records Paul's actual approval of **Gate 3: a 4D object and its moving 3D shadow**. That approval authorizes this gate only. This charter and its three companion contracts/predictions are frozen before actual browser trials. Generated expected states are not observations.

## Question and claims

Can a controlled additional projection expose a specified difference that a first shadow loses, and can the underlying point be recovered from the declared coordinate observations? The intended explanation is a known four-coordinate source transformed by an orthogonal x–w rotation and a fixed projection. Competing explanations or failures include decorative deformation, camera motion mistaken for source motion, ID swaps, artificial jitter, source data leaking into the recovery routine, or a readable animation without sufficient observations.

Keep three claims separate:

1. **Mathematical fidelity:** construction, source rotation, projection, invariants and reverse motion follow the frozen equations.
2. **Information recovery:** known raw 3D projected coordinates, known transformations and supplied point correspondences yield rank four for the declared two-view system; the fixed view and camera-only conditions cannot determine w.
3. **Human understanding:** not tested. Agent operation with access to model data is instrument verification, not a viewer comprehension result. Neither animation nor successful linear recovery establishes a uniquely four-dimensional physical cause.

The object and full coordinates are defined in `model-contract.md`; independently derived checkpoints and tolerances are in `independent-predictions.json`. The solid has dimension four, boundary three, skeleton one and vertex affine span four. A 2D screen displays a 3D orthographic projection of the four-coordinate model. The Gate 2 Hopf/reference model remains in its own preserved replay and is not silently reinterpreted as this tesseract.

## Fixed conditions and controls

The canonical run is 32 seconds with theta 0°→90°→0°, all16 vertices/32 edges, marked A=`v1110`, B=`v1111`, and selected edge `e-v1110-v1111`. Start paused at zero. Exact checkpoints are 0/8000/16000/24000/32000 ms; step1000 ms. Fixed P drops w after source rotation. The camera is yaw30°/pitch20°; viewBox640×420, center320/210 and scale80. No automatic camera orbit, fit-to-geometry rescaling, trail, decorative jitter or source clipping enters the canonical condition. Restrained identity colors are supplemented by IDs/labels. Reduced motion keeps manual controls available.

Target fixed capture viewport: 1280×720 CSS pixels, with actual values/DPR/scene rectangle recorded. Additional resize checks use a wider1280×900 and narrower960×720 viewport if supported; actual measured sizes, not requested sizes, are authoritative. A resized comparison starts a separately labeled display condition; it cannot silently replace the fixed-view comparison. The inspector and plain coordinate/edge listings may scroll inside bounded panels but must not widen the page. Record any remaining scroll burden or occlusion.

Turn through 4D and Look around independently override source angle and ordinary camera while pausing at the existing simulation cursor. They are labeled Exploration. Time control alone evaluates the saved trajectory. Restore/checkpoint clears overrides, restores canonical camera/source/selection/options and returns to the saved run. Projection is a recorded fixed P in this gate. The origin and intended/observed result of every consequential control operation are recorded.

## Capture and replay plan

Save originals for all meaningful states; the final packet selects **two to four actual inspected screenshots**, including a decisive failure if one occurs. Fixed-view comparison candidates are:

1. **C0, paused0s:** overlapped A/B, retained IDs and selected marked edge, fixed camera and visible run identity.
2. **C1, paused16s:** A/B separated by2 in raw3D projection under exactly the same camera/scale/viewport as C0.
3. **C2, active return:** during uninterrupted replay with16<t<32s, preferably near24s, record the exact observed integer time/angle and `playing` state. An exact24s manual checkpoint is additional evidence, not a substitute for observed active reverse playback.
4. **C3, comparison:** underdetermined fixed/camera-only result and rank4 known0+90 result, with solver assumptions/inputs inspectable. If the UI requires separate originals, keep both and choose the clearer final packet image.

Additional captures document all five checkpoints, camera-only intervention, source30°, actual viewport changes, failed attempts, saved-run reopening and historical Gate2. The replay-end state at32s is recorded separately from C2. Capture metadata binds every image to its actual run/build/state and original image dimensions. State restoration is exact within the same browser; visual comparison accepts platform raster/font differences only where geometry/legibility are unaffected. No video is claimed unless actually recorded with a supported tool.

Proposed **watch this** guide, to be adjusted only to observed controls/results: “Start paused at0s and inspect the two marked IDs at one shadow location. Replay: they separate as the source turns through4D, then reunite on return while the camera remains fixed. Use8/16/24s for exact states. Compare one shadow with the known0+90 coordinate observations; Look around changes the ordinary camera and cannot reveal w at source0.” This is a planned instruction, not a claim that trials passed.
